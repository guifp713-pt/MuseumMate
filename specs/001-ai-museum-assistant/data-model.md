# Phase 1 Data Model: AI Museum Assistant

This feature introduces no new persisted collection type. It adds one client-only
in-memory shape, one request/response DTO pair on a new backend endpoint, and a
narrow extension to the existing `analytics-event` content type.

## Assistant Conversation (client-side, in-memory only)

Lives entirely as a QML property on `ChatIAPanel.qml`. Never sent to Strapi as an
entity, never written to `QtQuick.LocalStorage`. Cleared only when the app process
ends (per FR-009).

| Field | Type | Notes |
|---|---|---|
| `messages` | array of **Assistant Message** | Ordered oldest → newest |

## Assistant Message (client-side, in-memory only)

One turn in the conversation — either the visitor's question or the assistant's reply.

| Field | Type | Notes |
|---|---|---|
| `id` | string | Client-generated (timestamp + counter), for QML `ListModel`/repeater keys |
| `role` | `"visitor"` \| `"assistant"` | |
| `text` | string | Rendered message content |
| `language` | enum: `pt`\|`en`\|`es`\|`fr` | Language the message was sent/answered in |
| `autoTranslated` | boolean | `assistant`-role messages only; drives the FR-015 indicator |
| `status` | `"sending"` \| `"sent"` \| `"error"` | Local UI state (spinner / retry affordance) |
| `timestamp` | ISO 8601 string | Local send/receive time |

Validation: empty/whitespace-only `text` is never added to `messages` for a visitor
turn (client-side guard per the spec's Assumptions — no network round trip).

## Backend request/response (not persisted — single HTTP exchange)

### `AssistantAskRequest`

| Field | Type | Required | Notes |
|---|---|---|---|
| `message` | string | yes | The visitor's current question. Non-empty (trimmed). |
| `language` | enum: `pt`\|`en`\|`es`\|`fr` | yes | Visitor's currently active app language |
| `sessionId` | string | yes | Device/session id already generated by the mobile app (see `AnalyticsHandler.js`), reused for the `analytics-event.sessionId` field |
| `history` | array of `{ role: "visitor"\|"assistant", text: string }` | no | Prior turns in the current session, oldest → newest, for follow-up context (FR-014). Backend does not persist this — it only exists for the duration of the request. |

### `AssistantAskResponse`

| Field | Type | Notes |
|---|---|---|
| `answer` | string | The assistant's reply text, already in `language` |
| `autoTranslated` | boolean | `true` when `answer` was produced via AI translation (FR-006) rather than official catalog content (FR-005) |
| `onTopic` | boolean | `false` when the assistant declined per FR-003; used by the backend itself to pick the analytics `eventType`, and returned so the client can style declines distinctly if desired |

Both DTOs are produced/consumed only within the new `api::assistant` controller —
they are not Strapi content-type schemas and have no `content-types/` directory.

## Museum Catalog Content (existing — read-only for this feature)

No schema changes. The backend's assistant controller reads the same populated
shape `ApiHandler.js` already fetches (entidade → tours/items/maps/areas/dictionary,
localized) to build the system prompt. This feature does not add, remove, or modify
any field on `entidade`, `tour`, `map`, `area`, `item`, or `dictionary`.

## AnalyticsEvent (existing content type — extended)

`backend/app/src/api/analytics-event/content-types/analytics-event/schema.json`
gets three new values appended to the existing `eventType` enumeration:

| New enum value | Written when |
|---|---|
| `assistant_question` | A structured response comes back with `onTopic: true` |
| `assistant_decline` | A structured response comes back with `onTopic: false` |
| `assistant_error` | The AI call fails, times out, or the catalog fetch fails |

All other existing fields on `analytics-event` are reused as-is for these new
event types:

| Field | Value for assistant events |
|---|---|
| `eventType` | one of the three values above |
| `timestamp` | server time at write |
| `sessionId` | reused from the same per-device session id the mobile app already generates (`AnalyticsHandler.js`'s device/session identifier), passed through in the request |
| `language` | the request's `language` |
| `itemId` / `tourId` | `null` — the assistant is not scoped to a single item/tour |
| `success` | `true` for `assistant_question`, `false` for `assistant_decline`/`assistant_error` |
| `metadata` | `{ "source": "assistant" }` — deliberately excludes the visitor's question text and the assistant's answer text (per the clarified privacy scope: usage metadata only, never message content) |
